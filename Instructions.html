Trellix Firewall → Microsoft Defender (GCC High)

How to run the migration script and what the output means.

Before you start: what this does and does not do

  • Creates one new policy in Microsoft Defender (Endpoint security → Firewall). It never edits or deletes anything that already exists.
  • Every rule it creates is Disabled. Nothing starts blocking or allowing traffic.
  • The new policy has zero device assignments. No endpoint is affected by running this.
  • Running it again does not create a duplicate — it re-checks the same policy and reports the same result.
  • Rules that can't be mapped automatically are listed as Open, with the reason. Nothing is guessed or faked to make numbers look better.

1Download the files

Get this toolkit from GitHub: github.com/Cyberlorians/mde-trellix-firewall-migration

Click the green Code button → Download ZIP, then extract it anywhere on your computer (for example your Desktop). You can also git clone it if you prefer. Either way, you'll end up with a folder containing this page, Deploy-TrellixFirewallRules.ps1 and a toolkit subfolder — keep them together.

2What you need

  • Windows computer with PowerShell 7.4+. Check with pwsh -v; if missing, get it from aka.ms/powershell.
  • Your GCC High tenant ID (Entra/Azure AD tenant GUID).
  • An account with permission to create Intune/Defender configuration policies in that tenant.
  • This whole downloaded folder kept together — don't move the files apart from each other.
  • Your Trellix ENS Firewall XML export — the exact same file this mapping was reviewed against.

3Add your Trellix XML export

Copy your Trellix ENS Firewall export XML into the same folder you just downloaded/extracted (easiest), or anywhere else on your computer. The script checks it is byte-for-byte the exact file this mapping was built and reviewed against, so don't edit or re-export it.

If you copy the file directly into the downloaded folder and leave the box above blank, the script will look for it automatically. Otherwise, fill in the full path above — it's added to the command for you in the next step.

4Run the script

Open the downloaded folder, right-click inside it and choose "Open in Terminal" (or open PowerShell and cd into the folder). Fill in your tenant ID and XML path above, then copy the command it builds for you:

pwsh -NoProfile -File .\Deploy-TrellixFirewallRules.ps1 -TenantId "11111111-2222-3333-4444-555555555555"

Want to see the rule counts first without signing in or changing anything? Add -PrepareOnly:

pwsh -NoProfile -File .\Deploy-TrellixFirewallRules.ps1 -TenantId "11111111-2222-3333-4444-555555555555" -PrepareOnly

5Sign in when prompted

The script will print a web address and a short code, for example:

To sign in, use a web browser to open the page https://login.microsoftonline.us/device and enter the code ABCD1234 to authenticate.

Open that address in any browser, enter the code, and sign in with an account that can create Intune/Defender policies in your GCC High tenant.

6Wait for it to publish and verify

The script publishes the policy, then reads it back from Microsoft to confirm it matches exactly and is still unassigned, before it tells you anything succeeded.

7Review the results

When it finishes, it saves a file named Results-<your tenant id>.html in the downloaded folder. Open it in any browser. It shows:

  • Mapped and deployed — every Trellix rule name next to its exact new Defender rule name, and a direct link to the policy.
  • Open — Trellix rules or rule groups that could not be mapped automatically, and the specific reason why.

8After this runs

The new policy is Disabled and unassigned on purpose. Before turning any rule on or assigning it to devices:

  • Review each rule inside the policy in the Defender portal.
  • Pick a small pilot group of devices to test with first.
  • Separately review everything listed as Open in the results — it represents real Trellix configuration that did not have a safe automatic Defender equivalent.

Questions / troubleshooting

The script stopped with an error

It is telling you exactly what it refused to do and why (for example: wrong XML file, or a previous run's files changed on disk). It does not silently continue after an error — fix what it reports and rerun.

It says the XML doesn't match / "does not match the file this mapping was reviewed against"

This migration was built and reviewed against one specific export. If your file has since been re-exported from Trellix (even with no visible changes), its checksum will differ and the script will stop rather than silently map against unreviewed data. Use the original file, or have the mapping reviewed again against the new export.

Can I run this more than once?

Yes. It reuses the same policy rather than creating a duplicate, and re-verifies it is still correct and unassigned.

Does this turn anything on?

No. Every rule it creates is Disabled, and the policy is never assigned to any device by this script.
